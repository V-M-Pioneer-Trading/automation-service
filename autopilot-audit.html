The short version

what the review actually turned up

This codebase is unusually thoughtful about the hard parts of autonomous automation. Scoring is pure and replayable, the one-atomic-action-per-tick invariant is real and consistently held, and the abort/pause/shadow discard checks are re-verified after every await window — that is care most services never spend.

The failures cluster somewhere less flattering: the safety properties the documentation is proudest of are the ones that don't hold. The knob-class fence that supposedly keeps an AI supervisor away from its own alarm thresholds is a read filter with no write-side check. The weights documented as disabling a task kind don't disable it. The cash floor that prevents the unrecoverable death spiral ships set to zero. And the alarm for a dead fleet switches itself off after about six hours.

None of these are subtle once you look, and three of them I confirmed by running the real code rather than reading it. The pattern is worth naming: each is a case where a mechanism was built correctly and then not wired to the thing it protects.

Critical

safety or governance claims that do not hold

01

The knob-class fence is a read filter — nothing checks class on write

Principle
src/server.ts:298 · src/knobs.ts:299 · src/__tests__/knobClasses.test.ts

knobs.ts states the design plainly: alert thresholds are held "deliberately out of the AI's reach", because "an agent that can widen its own alarm thresholds will eventually resolve 'profit dropped' by deciding profit drops are fine." The README repeats it as a three-class permission table.

PUT /planner/knobs/:name performs no class check at all, and KnobRepo.set validates only bounds. The sole enforcement anywhere is GET /planner/knobs?class=policy narrowing what the supervisor is shown. There is also no authentication on any route in the service — no middleware, no token check beyond the SpaceTraders credential forwarded downstream.

The test file written to hold this line makes the gap concrete. Its header comment reads "Knob classes are the fence around the AI supervisor: it may write policy and nothing else." It contains no test that a model or alert write is rejected. Both of its write tests assert the write succeeds — including one titled "still lets an operator write a model knob directly", which is indistinguishable from the AI doing it.

How it fails

The supervisor reads the README (or guesses a name from the digest it already receives), issues PUT /planner/knobs/anomaly.errorRateThreshold {"value": 1}, and the fleet's error alarm can never fire again. Nothing rejects it, nothing flags it — it lands in the audit log as an ordinary knob_changed event.

Fixing this needs the write path to know who is calling, which means the service needs real authn/authz before the class distinction can mean anything. Until then the three-class model is documentation, not a control.

02

Setting a task weight to zero does not disable that task kind

Correctness Verified live
src/planner.ts:322 · src/scoring.ts:54 · src/knobs.ts:101

Both knob descriptions and the README promise an off switch: mine.taskWeight — "0 disables mining entirely"; contract.taskWeight — "0 disables contract work."

A zero weight makes miningScore return 0, not -Infinity. In assignTarget, an absent competitor scores -Infinity, so zero still wins the comparison, and the planner dispatches the ship.

How it fails

I ran the real Planner against stub clients. With mine.taskWeight = 0, no accepted contracts, and scouting off, the assignment returned kind: "mine" → X1-AB-BELT. With contract.taskWeight = 0 and no reachable asteroid, it returned kind: "contract" → C-1. An operator killing mining during an incident watches the ship keep mining.

scoring.test.ts asserts the function returns 0 for a zero weight. Nothing tests what the planner then does with that 0, which is where the promise actually lives. scout.creditsPerRefresh is the one weight that genuinely disables its task, because it has an explicit > 0 guard — the other two need the same.

03

Ship dispatch has no distributed lock, and the README under-states the risk

Correctness
src/scheduler.ts:76 · README.md "Known limitations → Operations"

The re-entrancy guard that prevents two ticks racing the same ship_task row is an in-memory boolean on the scheduler instance. It protects against one process overlapping itself. It does nothing across processes.

The known-limitations list acknowledges that "metrics rollups assume a single instance" — a double-counted reporting number. It does not mention that the same assumption governs ship dispatch. Two replicas both read MINING_SHIP_SYMBOL from env and both drive it.

How it fails

Scale the deployment to two replicas. Both schedulers reach CONTRACT_PURCHASE for the same ship in the same window and each dispatches purchase — the agent buys twice the goods for twice the credits, and the reserve-floor check that cleared the trip only ever accounted for one of them. The same shape applies to deliverContract and sell.

This is the single largest gap between the documented blast radius and the real one. The ceiling on damage today is enforced by the deployment being single-instance, not by the design — and nothing in the code would tell you if that changed.

04

The cash floor that prevents the unrecoverable failure ships disabled

Fail-safe
src/knobs.ts:146 · src/scoring.ts:115

scoring.ts is explicit about the stakes: "Running out of credits with no fuel money is the classic SpaceTraders death spiral, and it is not recoverable in-game." The floor exists, it is checked on every mining, contract and scout candidate, and the check is correct.

credit.reserveFloor defaults to 0. At zero, breachesReserveFloor reduces to "would this take the balance negative" — it blocks only work the agent already cannot afford, and reserves nothing at all. Every fresh deployment runs with the guard nominally on and functionally absent until somebody thinks to set it.

How it fails

A fleet on default knobs spends down to a handful of credits, takes one trip whose real fuel cost exceeds the estimate (the fuel rate is a prior until a refuel transaction reports a price — see finding 07's sibling problem), and strands. There is no recovery path and no alarm specific to it.

A safety default should cost something to turn off, not something to turn on. Even a conservative non-zero default — a few thousand credits, or a multiple of the measured per-cycle fuel cost — would make the mechanism do what its own comment says it is for.

Correctness

the model decides on inputs that don't mean what it thinks

05

Market freshness is tracked by two subsystems that never tell each other anything

Correctness Verified live
src/scheduler.ts:304 · src/miningTask.ts:253 · src/planner.ts:427 · src/anomaly.ts:285

getMarket is called from four places in this codebase. Mining's findBestMarket prices every marketplace in the system on every cycle. evaluateContract does the same on every contract evaluation. The scout FSM prices one. And MarketIntelRepo.record — the table the planner scores staleness from — is called from exactly one of those four.

Both directions of the resulting split are broken:

The planner scouts markets that were just refreshed. Mining re-prices the whole system every cycle without recording any of it, so market_intel believes those markets are aging. Staleness grows linearly and without bound, so the planner eventually scores a scouting trip above real work and spends a ship on flying to refresh data it already refreshed minutes ago. This is structural — it recurs forever, not once.

The alarm never clears when scouting fixes the problem. checkMarketStaleness reads only mining_market_selected events' marketsChecked array. A scout_market_refresh is invisible to it. A market that the scouting subsystem is successfully keeping current keeps raising market_stale every cooldown window.

How it fails

Scouting is enabled by default at 500 credits per refresh. On a fleet where mining already prices every market each cycle, every scout trip the planner schedules is wasted fuel and wasted cycle time — and the anomaly it was supposed to resolve keeps paging the operator regardless.

One concept, two sources of truth, neither authoritative. Recording intel wherever getMarket is actually called, and reading the same table in the anomaly check, collapses both halves.

06

A single observation sets a field's revenue estimate outright

Correctness
src/observations.ts:207 · src/observations.ts:250 · README.md:96

The README claims recency weighting delivers adaptation "without one lucky trip swinging the estimate." Decay does not provide that. weightedMean over a single sample returns that sample exactly — there is no shrinkage toward the fleet mean, no minimum sample count, and no confidence term anywhere downstream.

The model already computes the information needed to fix this and then discards it. provenance.miningSampleCount and waypointsWithOwnAverage are assembled, logged, and served over GET /planner/model — and never consulted by any scoring path. A field with one observation and a field with forty are treated as equally authoritative.

How it fails

One anomalously rich cycle at a distant field — a good survey, a temporary price spike — sets creditsPerCycleByWaypoint high enough to beat a closer, well-measured field. Because the planner always picks the argmax, it returns there, and the estimate is only corrected by cycles that the estimate itself caused. There is no exploration term; the correction arrives when the observation decays out, up to fourteen days later.

The provenance plumbing means this is a small change: weight a per-waypoint average toward fleetCreditsPerCycle by sample count, and the cold-start behaviour the README promises falls out for free.

07

Contract scores are frozen under a model that has since moved

Correctness
src/planner.ts:99 · src/planner.ts:266 · src/contractScheduler.ts:82

loadContext carries an explicit promise: inputs are gathered once "so every task kind is scored against exactly the same snapshot of the world." That holds for mining and scouting. It does not hold for contracts.

A contract's expectedProfit and cycleHours are computed once at discovery, against whatever the calibrated model believed then, and frozen into the contract row. Every later comparison scores that frozen pair against mining numbers computed from the current model. Only contract.taskWeight is applied live — so the contract arm is half-fresh and half-stale.

How it fails

A contract discovered on a cold fleet is evaluated at the prior speed of 30 units/hour. Real flights then calibrate speed to 60. Every mining score doubles; the contract's score does not move. A contract that was genuinely the best available work is now systematically out-competed — or, if the calibration moved the other way, keeps winning on numbers the fleet has already disproved.

08

Mining's measured overhead is charged to scout and contract cycles

Correctness
src/observations.ts:193 · src/scoring.ts:102 · src/planner.ts:478

overheadHours is derived as the residual of mining cycle time — the module's own comment names its components: "survey + extract + cooldown + dock + sell." Deriving it that way is the right call for mining, and keeps the model self-consistent.

That same number is then added to the scout cycle (dock, one getMarket call) and to the contract cycle (dock, purchase, deliver, fulfil). Neither performs a survey, an extraction, or a cooldown. The three task kinds are compared in credits-per-hour, and one kind's fixed costs are being billed to all three.

How it fails

On a fleet where measured mining overhead lands near the README's worked example of 0.42h, a scout trip of ten minutes' flight is scored as though it takes thirty-five — understating scouting's rate by roughly two-thirds and biasing every comparison toward mining. The bias is systematic, not noise, and it grows as measured overhead grows.

Related and smaller: scouting is scored on one-way distance while mining is scored round-trip. That is deliberate and documented, but it does mean the score omits the cost of the ship being left wherever the scout ended, which the next assignment then pays.

09

A dead fleet stops alarming after about six hours

Detection
src/anomaly.ts:172 · src/anomaly.ts:234 · src/anomalyScheduler.ts:146

Consider a fleet left paused — an operator pausing to investigate and getting pulled away, which is the single most likely way this service ends up quietly doing nothing. Trace what each check does as the hours pass:

ship_idle requires armed && live, so it is skipped entirely. credits_flat reads agent_credits_snapshot events, which are only written while armed && live — so snapshots stop, and once the window passes the last one, baseline and current resolve to the same row and the check returns null by design. profit_drop does fire: rollups keep running, the latest rate goes to zero against a healthy trailing average.

How it fails

After roughly six hours the trailing six-hour average has itself decayed to zero, and detectProfitDrop hits its if (avg6h <= 0) return null guard. Every check is now silent. A fleet that has earned nothing for a day is indistinguishable, to every alarm in the system, from a healthy one — and the alarm went quiet precisely when the outage stopped being transient and became chronic.

The guards are individually reasonable; each avoids a real false positive. The gap is that nothing asserts the positive condition — that a fleet which is supposed to be working is in fact earning. A check on "armed-but-not-live for longer than N minutes", or one on absolute rather than relative earnings, closes it.

Limitations

real, lower-severity, worth knowing before scaling

10

Redeploys silently clamp tuned values, including safety ones, with no audit event

Auditability
src/db.ts:52 · src/server.ts:310

syncKnobDefinitions clamps any stored value that no longer fits tightened bounds. The reasoning is sound — better than leaving a value the write path would reject. But every API-driven change writes a knob_changed event, and this one writes nothing.

How it fails

An operator sets credit.reserveFloor to 500,000. A later release tightens the maximum to 100,000. The floor drops by 400,000 credits on boot; the event log still shows the operator's 500,000 as the last intended value. The audit trail and the running configuration disagree, and nothing points at the moment they diverged.

11

A failed anomaly delivery is persisted and then never retried

Detection
src/anomalyScheduler.ts:134 · src/anomaly.ts:55

Anomalies are recorded before delivery is attempted — the right order, and the README is right to call it out. Three attempts run inside the tick; on failure incrementDeliveryAttempts is called and the loop moves on. delivered_at stays null forever. Nothing ever scans for undelivered rows.

How it fails

The webhook is down for a minute during a transient problem. All three attempts fail, dedupe then suppresses re-firing for the cooldown, and by the time the cooldown expires the condition has cleared. The page is lost permanently — the row is safely in Postgres, which is exactly what makes the loss invisible.

12

Replan is sequential and re-runs full contract discovery once per idle ship

Scaling
src/scheduler.ts:359 · src/scheduler.ts:406 · README.md:452

runReplan awaits assignTarget per ship in a plain loop, and every assignTarget opens with discoverAndEvaluateContracts — which fetches all contracts and, for anything unseen, prices every marketplace in the system.

The README says the planner and listIdle() "scale to N ships without further changes." The scoring does. The dispatch loop does not: N idle ships produce N sequential full discovery passes inside a single tick, behind a re-entrancy guard that blocks all other dispatch until it finishes.

How it fails

This is the first thing that breaks when multi-ship arrives. Eight idle ships at a five-second tick interval means eight redundant contract-discovery round trips before the first ship moves — and the tick guard means the fleet stops progressing while it happens.

13

The observation cap can silently erase a field's own average

Scaling
src/observations.ts:27 · src/observations.ts:120

recentMining takes the 500 newest rows fleet-wide, then groups by waypoint. On a busy fleet, a rarely-mined field's observations fall outside that window even though they are well inside the fourteen-day age limit, and it reverts to the fleet average.

How it fails

A field measured as poor drops out of the sample, reverts to the (higher) fleet average, and becomes attractive again — so the fleet re-learns the same disappointment periodically. waypointsWithOwnAverage simply stops listing it, with no signal that the omission is a cap artifact rather than a genuine absence of data.

Principles scorecard

against the practices autonomous, money-moving automation is held to

Principle Verdict Evidence
Human-in-the-loop / kill switch Holds Arm/pause/abort is re-checked after every await window, on success and failure paths alike. Abort awaits the in-flight tick before returning. Shadow→live requires explicit re-arm. Genuinely well built.
Least privilege Fails Finding 01. The class model is enforced on reads only, and the service has no authentication to distinguish operator from agent in the first place.
Fail-safe defaults Partial Cold-start priors and "no viable target → idle" both fail toward inaction, correctly. The reserve floor (04) ships at zero, and the task-weight off switches don't switch anything off (02).
Idempotency / crash safety Holds Contract-assign and ship_task save share one transaction. Orphaned-accept reconciliation in contractScheduler handles the non-atomic accept/record boundary explicitly rather than hoping. Per-phase persistence resumes cleanly.
Graceful degradation Holds Contract discovery failures are logged and ignored — contracts stay additive to mining, never a dependency. Observation writes are best-effort and can't fail a successful ship action. Upstream calls carry timeouts.
Auditability Partial Decision inputs and provenance are logged thoroughly enough to genuinely reconstruct a choice. Undercut by silent clamping (10) and by POST /events letting the supervisor write into the same digest it later reads as context.
Configuration vs. code Partial Knob coverage is good and the class taxonomy is the right idea. But market_stale's 24h active-use window, the 500-row observation cap, and the 14-day age limit are all buried constants with operational consequences.
Testability Partial Real Postgres, stub upstreams, injectable clock, pure scoring — the seams are right. Coverage concentrates on happy paths: the governance fence has no negative test (01), and the planner's dispatch decision is untested at the weights where it misbehaves (02).
Blast-radius containment Fails Today's ceiling comes from the deployment being single-ship and single-instance, not from the design. Finding 03 shows it disappears silently on the first horizontal scale-out, with no code-level signal.

Worth keeping

design decisions that earned their complexity

  • Pure scoring plus logged inputs plus replay. The triad is rare and it works. Better still, formatReport warns when a zero-override replay changes any decision — it detects its own drift and says so loudly, rather than quietly producing wrong answers. That instinct is the reason the rest of the audit could be done by reading.
  • One atomic action per tick. Held consistently across all three FSMs, and it is what makes pause a clean operation instead of a hopeful one. The invariant is stated as a safety property rather than an optimisation, which is the correct framing.
  • Discard-after-abort on both paths. The success path and the failure path both re-verify liveness before mutating state. Most codebases remember the first and forget the second.
  • Provenance on every calibrated value. Recording whether a number was measured or assumed is the difference between a decision you can defend and one you can only explain. The flaw in finding 06 is that provenance is recorded and then not used — the hard half is already done.
  • Contract discovery folded inline rather than scheduled. The comment explains the race that killed the background version. Documenting why the obvious design was rejected is worth more than the code itself.

Findings 02, 03 and 05 were confirmed by executing the code or enumerating call sites, not by reading alone. Finding 02 was reproduced against the real Planner class with stubbed clients. Everything else follows from close reading and is cited to file and line.
